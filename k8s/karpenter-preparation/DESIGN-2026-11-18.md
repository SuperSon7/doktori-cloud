# Self-managed Kubernetes에 Karpenter를 도입하기 전 준비

2026-11-18 · 저장소와 공식 문서를 바탕으로 작성한 설계·설정 초안이다. 실제 클러스터, AWS 계정, 설치 버전, 장애 상태를 조회하지 않았다. 아래 시나리오는 앞으로 검증할 가설이며 장애를 재현했다는 뜻이 아니다.

## 먼저 결정한 방향

기존 고정 worker 중 일부를 시스템용으로 유지하고, 별도 Karpenter NodePool에서 일반 업무 Pod의 확장을 시험한다. controller·CoreDNS·Calico 등 필수 구성요소와 외부 유입 경로를 먼저 안정적으로 유지해야 새 노드를 만들 수 있다. 첫 도입은 on-demand·ARM64·전용 canary taint로 제한한다. Chat과 실제 업무 트래픽을 옮기는 일은 노드 등록·네트워크·drain 검증 뒤로 둔다.

Calico와 AWS 자격증명은 서로 다른 구성이다. Calico는 Pod IP·노드 간 통신을 담당하고, AWS IAM은 Karpenter가 EC2 API를 호출할 권한을 결정한다. VPC CNI를 사용하지 않는다는 이유로 OIDC가 필수가 되는 것은 아니다. 이번에는 노드 IAM role을 Pod가 공유하는 방식을 줄이기 위해 **ServiceAccount 토큰 → STS → controller 전용 IAM role**을 준비한다. self-managed 클러스터이므로 issuer·공개 키 배포·IAM trust·Pod token 주입을 직접 운영해야 한다. [AWS self-hosted 지침](https://github.com/aws/amazon-eks-pod-identity-webhook/blob/master/SELF_HOSTED_SETUP.md)

## 어떤 상황에서 문제가 생길 수 있는가

모든 행의 상태는 **미실행**이다. 성공 기준은 최초 검증을 위한 후보이며 시간·오류율의 업무 허용치는 후속 실험 전에 정한다.

| 시나리오·유발 조건 | 예상 증상과 원인 | 나중에 볼 증거·합격 기준 | 준비할 조치 |
| --- | --- | --- | --- |
| 현재 고정 용량을 넘는 동시 접속 | HPA가 Pod를 늘려도 Pending. CPU/메모리 requests를 수용할 노드가 없음 | HPA desired, Pending 이유, allocatable/requests와 사용자 지연을 같은 시각으로 비교 | 기준선 측정 후 canary NodePool의 확장과 비교 |
| HPA 지표가 사라짐 | Karpenter를 설치해도 Pod replica가 늘지 않아 요청이 몰림 | metrics-server/adapter 오류와 HPA conditions. 복수 지표의 실패를 무조건 정상 fallback으로 단정하지 않음 | 지표 장애와 노드 부족을 따로 실험 |
| 최초 구축 하루 뒤 새 worker 필요 | EC2는 Running인데 join 실패. 현재 생성 명령은 TTL을 지정하지 않음 | token 만료 시각·bootstrap 종료 코드·NodeClaim Registered. kubeadm 기본 TTL은 24h [공식 문서](https://kubernetes.io/docs/reference/setup-tools/kubeadm/kubeadm-token/) | 짧은 수명 join 정보 갱신기·원자적 SSM 교체·잔여 TTL 기준·만료 경보 설계 |

| OIDC 주소·kid·aud·sub 불일치 | STS InvalidIdentityToken/AccessDenied, 새 노드 생성 불가 | 자격증명 probe의 role ARN, STS 오류 코드, issuer/JWKS 공개 응답. 토큰 원문은 저장 금지 | 정확한 issuer·JWKS·trust, 시간 동기화·키 회전 overlap |

Custom AMI는 자동 bootstrap 병합이 없으며 등록 taint와 kubelet 설정의 책임이 사용자에게 있다. [NodeClass Custom 요구사항](https://karpenter.sh/docs/concepts/nodeclasses/#custom). Disruption budget은 모든 강제 중단을 막는 장치가 아니다. [중단 방식과 제한](https://karpenter.sh/docs/concepts/disruption/)

## 버전은 어떻게 확인할 것인가

현재 검토 경로에서 Karpenter 설치 선언을 찾지 못했으므로 “현재 Karpenter 버그”는 판정할 수 없다. Kubernetes도 1.34 계열 선언과 AMI 설명만 확인했다. [공식 호환표](https://karpenter.sh/docs/upgrading/compatibility/)의 1.34 최소 조건은 Karpenter >=1.6이지만, 최소 조건은 오늘의 권장 patch나 무결함 보장이 아니다.

템플릿의 문법 참조는 **v1.15.2 chart/source**로 고정했다. 도입 버전으로 확정한 것이 아니다. 도입 시에는 실제 kubelet/apiserver/Calico/CSI·AMI 버전, Karpenter 지원 기간·release note·보안 공지와 Custom kubeadm 관련 issue를 다시 대조해 patch를 결정한다. `latest`나 AMI alias 자동 갱신을 적용하지 않는다. v1.15.2의 [values](https://github.com/aws/karpenter-provider-aws/blob/v1.15.2/charts/karpenter/values.yaml), [Deployment template](https://github.com/aws/karpenter-provider-aws/blob/v1.15.2/charts/karpenter/templates/deployment.yaml), [provider options](https://github.com/aws/karpenter-provider-aws/blob/v1.15.2/pkg/operator/options/options.go)를 읽어 직접 token mount와 non-EKS 옵션을 대조했다. 이 조합이 실제 독토리에서 동작한다는 보장은 아직 없다.

## OIDC와 자격증명 준비

인증은 세 경로로 나눈다. controller는 Kubernetes API를 ServiceAccount/RBAC로 호출하고 AWS는 STS 임시 자격증명으로 호출한다. 새 EC2는 별도 node instance profile로 bootstrap SSM·ECR 등을 사용한다. kubeadm 가입 인증은 AWS role이 아니라 bootstrap token·cluster CA를 사용한다. EKS `aws-auth`나 EKS access entry를 복사해도 kubeadm 가입을 대신하지 않는다.

| 준비물 | 설정과 소유 책임 | 아직 필요한 값 |
| --- | --- | --- |
| issuer HTTPS 주소 | public discovery/JWKS만 STS에서 접근 가능하게 제공. 예: private S3+CloudFront OAC+HTTPS. API endpoint/etcd/개인키를 공개하지 않음 | 실제 DNS·TLS·호스팅·가용성·운영 주체 |
| Kubernetes 토큰 서명 | 모든 apiserver의 issuer·서명/검증 key 일치. 실제 API가 내보내는 discovery/JWKS와 token kid 대조 | 기존 issuer/audiences·키 회전 방식. 이번에 키를 읽거나 생성하지 않음 |
| IAM OIDC provider | issuer URL과 `sts.amazonaws.com` client ID. 기존 동일 issuer provider가 있으면 재사용/import 검토 | 계정·issuer·TLS chain. thumbprint는 임의 값 금지 |
| trust policy | `sts:AssumeRoleWithWebIdentity`, 정확한 `aud`, `sub=system:serviceaccount:karpenter:karpenter` | 생성된 `controller-trust.json.example` 참조 |
| Pod token | audience STS, TTL 3600, projected volume, role ARN/token file 환경변수 | Helm rendering 후 SDK가 갱신된 파일을 재사용하는지 확인 |
| Kubernetes API token | chart의 기본 API용 SA mount 보존. STS token으로 대체하지 않음 | 기존 API audiences 유지 |
| controller EC2 권한 | 고정 provider 버전의 upstream 정책을 출발점으로 검토. Describe 계열, CreateFleet/RunInstances/LaunchTemplate/CreateTags, tag 제한 Terminate/Delete, 정확한 node role의 PassRole | 실제 subnet/SG/AMI·cluster tags·instance profile. trust만 만든 현재 초안에는 권한을 붙이지 않음 |
| node IAM | node role의 EC2 trust+instance profile. 지정 join parameter 읽기/필요 KMS decrypt, ECR pull, 필요한 운영 agent만 | 앱 SSM/S3 권한을 자동 승계하지 않음 |

[IAM OIDC 요구사항](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_roles_providers_create_oidc.html), [ServiceAccount token projection·issuer discovery](https://kubernetes.io/docs/tasks/configure-pod-container/configure-service-account/), [Karpenter IAM 정책의 역할별 설명](https://karpenter.sh/docs/reference/cloudformation/)을 근거로 한다. SDK credential 설정만으로 권한이 생기지 않으므로 trust와 permission policy를 별도로 검토한다.

기존 API 서버에 `--oidc-issuer-url`을 넣는 사용자 로그인 설정과 SA 서명용 `--service-account-issuer`는 다르다. `apiserver-merge-fragment`는 후자다. 기존 kubeadm ClusterConfiguration에 병합해야 하며 전체 설정을 덮어쓰면 안 된다. issuer 변경 시 새 issuer를 먼저 발급에 사용하고 기존 issuer를 수락하는 기간을 둔다. 기존 API audiences를 STS 하나로 바꾸지 않는다. 모든 control plane의 검증 key를 맞추고 정상 API 인증·기존 토큰 갱신을 확인한 뒤 이전 issuer/key를 단계적으로 제거한다. 공개 JWKS는 이전 토큰 수명·캐시 기간 동안 이전 키도 제공해야 한다.

AWS의 오래된 self-hosted 문서에는 Kubernetes에 discovery endpoint가 없던 시기와 public S3 ACL 예제가 들어 있다. 그대로 실행하지 않는다. 현대 Kubernetes의 discovery/JWKS를 기준으로 공개 자료만 호스팅한다. `sa.key`, JWT, kubeconfig, join token은 저장소·Terraform 변수/state·userData·로그에 넣지 않는다. 공개 JWKS를 만드는 단계도 실제 키를 확인하는 후속 작업으로 남겼다.

직접 주입은 Karpenter 한 workload를 준비할 때 구성요소가 적다. 여러 서비스에 적용하려면 IRSA용 pod-identity-webhook과 인증서·admission failure policy 운영을 비교한다. 이 webhook은 EKS Pod Identity Agent/association과 다른 기능이다. 장기 access key Secret은 기본안에서 제외한다. node instance profile 공유도 가능한 경로지만 Pod 권한 격리와 IMDS 의존이 남는다.

## CNI·bootstrap 설정에서 빠뜨리면 안 되는 것

`hostNetwork`는 Calico라는 이름만 보고 켜지 않는다. chart 주석은 custom CNI를 언급하지만 이 self-managed control plane의 실제 Pod 경로가 판단 기준이다. 초안은 false로 두고 API·DNS·STS 경로를 먼저 시험한다. hostNetwork가 필요해지면 ClusterFirstWithHostNet·host port·NetworkPolicy 적용 범위·IMDS 접근까지 같이 바꿔 검증한다.

Custom AMI의 `kubeadm join`은 보안상 중요하다. 부팅 시 IMDSv2로 EC2 ID/AZ/private DNS를 얻고, 전용 node role로 지정 SSM parameter의 구조화된 join 설정을 읽는다. 토큰 만료 여유와 API endpoint/CA hash를 검증한 다음 root 전용 임시 파일로 실행하고 제거한다. 로그에는 token/config 본문을 남기지 않는다. SSM 갱신기는 만료 전에 새 token을 생성·반영하고 기존 가입 시도와 겹칠 시간을 둔다. 전체 AWS 권한이나 admin kubeconfig를 worker에 배포하지 않는다.

`providerID`·hostname과 EC2 식별자가 맞아야 한다. `--cloud-provider=external`만 추가하면 CCM이 없을 때 uninitialized taint가 남을 수 있다. AWS CCM 도입 여부는 별도 결정이며 Karpenter가 LoadBalancer/CSI 기능까지 대체하지 않는다. zone/instance labels·CSINode·volume topology도 후속 노드 등록 검사에 포함한다. `karpenter.sh/unregistered` taint는 controller가 처리하며, canary taint는 시험 Pod만 toleration을 갖도록 유지한다.

새 SG는 기존 worker/master와 양방향 통신할 수 있어야 한다. STS·EC2·SSM·ECR API/DKR·S3, DNS/NTP와 선택적 SQS/가격 조회 경로를 NAT 또는 해당 VPC endpoint로 설계한다. issuer 공개 자료를 읽는 주체는 STS이고, controller가 호출하는 것은 STS endpoint라는 점도 구분한다. NAT 없는 환경에서는 IAM instance-profile 동적 생성 같은 호출 제약을 고려해 사전 생성 profile을 사용한다.

## 준비한 파일과 후속 적용 순서

이 디렉터리는 ArgoCD Application·기존 deploy script·Terraform root에 연결하지 않았다. `render.py`는 표준 파일 I/O와 YAML 출력만 사용한다. AWS/kubectl/helm/SSM을 실행하지 않는다.

```powershell
# cloud 저장소 루트, Python 3.11+/PyYAML 6.x. output은 새 디렉터리여야 한다.
python k8s/karpenter-preparation/render.py --input k8s/karpenter-preparation/inputs.example.json --output k8s/karpenter-preparation/.generated-review
```

| 산출물 | 사용 목적·현재 한계 |
| --- | --- |
| [inputs.example.json](inputs.example.json) | 실제 계정/AMI 대신 placeholder. 배포 승인 false |
| [render.py](render.py) | trust/discovery, Helm values, NodePool/EC2NodeClass, apiserver 병합 조각, JoinConfiguration 총 7개 `.example` 생성 |
| [identity.tf.example](identity.tf.example) | 독립 IAM provider·trust role IaC 초안. permission policy·공개 호스팅은 아직 연결하지 않음 |
| 생성 Helm values | 고정 system label로 2 replica 배치, STS token 직접 mount, node-role fallback 억제. chart 기본 호스트 분산 조건도 확인 필요 |
| 생성 NodePool | ARM64 on-demand canary, CPU8/32Gi, voluntary budget0, expire Never. 실제 용량 추천값이나 비용 상한 보장 아님 |
| 생성 EC2NodeClass | 고정 AMI·subnet/SG·사전 생성 profile·maxPods30. userData는 의도적으로 exit78. 검토한 custom bootstrap으로 교체 전 적용 불가 |
| 생성 join template | 비밀 없는 형식 계약. 실제 short-lived token 발급/갱신기·부팅 helper 구현은 후속 |

후속 순서는 (1) 실제 버전·현재 리소스 증거 수집 → (2) baseline 포화/지표 장애 시나리오 → (3) OIDC 공개 자료·trust·토큰 갱신 검증 → (4) IAM 정책·system worker·Custom AMI/bootstrap 완성 → (5) on-demand canary 1개 가입·네트워크·이미지 pull → (6) API 확장/축소·ALB 유입 → (7) Chat drain → (8) Spot·drift·업그레이드다. 각 단계에서 확인한 시각과 Pod Pending→EC2 launch→Node Registered→Initialized→Pod Ready→업무 성공 시간을 기록한다. stage별 SLO와 비용 한도를 정한 뒤 실험한다.

rollback은 새 canary Pod 유입을 멈추고 기존 고정 ASG 용량으로 되돌린 뒤 Pod와 실제 EC2/NodeClaim을 확인하는 순서로 설계한다. NodePool 삭제는 소속 노드 종료를 유발할 수 있으므로 “컨트롤러 끄기”와 같은 조치로 취급하지 않는다. controller를 먼저 제거하면 finalizer/EC2 정리가 남을 수 있다. 이 초안에는 삭제·설치 실행기를 넣지 않았다.
